# Security and trust model

## Scope

This is a powerful self-hosted account manager. A Telegram user session is effectively an account credential, not a narrowly scoped Bot API permission. Use only accounts whose actual owners have knowingly authorized your deployment and its pooled customer tasks. Telegram may ban or limit accounts. Do not use fake participants to deceive others, spam join requests, bypass restrictions, harvest credentials or sell access to stolen sessions.

## Roles and authorization

Owner IDs are loaded only from trusted deployment JSON or explicit owner-ID service Variables; no default owner is invented. Validated environment values override matching file fields. Admin roles are in Mongo and rechecked for every privileged action (including every login step/approval). Premium eligibility is checked on job creation, before actual joins/rejoins, and during active calls. Target control is verified via Telegram Bot API admin membership before execution and periodically during calls.

Admins cannot manage another admin's account session. Owners can operate all registered sessions, so an owner or server/database/encryption-key compromise must be treated as account compromise. Removed admin roles immediately lose UI/login privileges; existing authorized pool sessions remain under owner management until disabled/removed/revoked.

## Sign-in — private-chat default (1.0.2)

- Only currently authorized owner/admin in their own private bot chat may start login. Customers cannot gain it from Premium. Consent/input/QR checks revalidate actor and fresh nonce.
- The consent screen identifies your self-hosted full-session manager, not an official Telegram login service. Use only owned/explicitly authorized accounts.
- **Bot chats are not end-to-end encrypted.** Phone/OTP/2FA and QR tokens travel through Telegram Bot API/server infrastructure; Telegram/the trusted operator may access or retain them. Deletion is best effort, not guaranteed erasure of server/client/notification copies. This requested trade-off is not equivalent to local/trusted HTTPS secret entry.
- Inputs are deleted best effort before processing; deletion failures do not serialize the event. No raw phone/code hash/OTP/password/QR token goes into Mongo, audit, application logs or FSM. FSM holds only random context ID; client/phone hash are short-lived RAM. Logs retain authored phase/type/stack filenames/lines, not exception messages.
- Telegram may invalidate a code posted in chat. Do not encode/disguise/split codes to defeat this protection. QR uses the official authorized-device approval protocol instead of collecting OTP; 2FA may follow.
- QR images/links are credential-like, short-lived and removed best effort after check/cancel/expiry. No durable token outbox/files. Never forward a token or approve a login you did not initiate.
- Dialogs expire in 10 minutes, limit attempts, reject simultaneous operations/forwarded credentials. Cancel/navigation/role loss/expiry clean up; authorized-but-unsaved clients are logged out best effort. Saved sessions are not revoked by a later disconnect/UI/notification failure.
- Re-auth validates original account ID/management rights/busy state, claims the account against simultaneous staff re-auth, and disables old session only after consent.
- Login FloodWait creates RAM+Mongo actor cooldown across fresh dialogs/restarts. SDK migration has bounded follow-up attempts; positive FloodWait surfaces instead of being hidden/slept through.
- Only phone last four digits, Telegram ID and display name are stored. Python/native memory zeroization is not guaranteed; host compromise exposes RAM/sessions.

Optional legacy **LOGIN_MODE=browser** is explicit trusted-deployment opt-in: one-use hashed 5-minute fragment tickets, matching browser-code approval, 10-minute contexts, HTTPS-only Host/Origin, secure cookies/CSRF, bounded non-reflecting bodies, CSP/no third-party JS/no cache/referrer/frames. Default chat mode denies /login and /api/login/* with 410; health remains. Never collect customers' credentials through unrelated phishing pages/bots.

## Stored sessions

Fernet provides authenticated symmetric encryption with fresh randomness before a StringSession is written to Mongo. The unique key is generated by setup and supplied via environment references in external JSON. No panel exports plaintext sessions. Plaintext sessions exist in the authenticated runtime's RAM because Telethon must use them.

Keep `.env` private and backed up. Changing the encryption key without re-encryption makes prior sessions unreadable. Compromise response: stop automation, revoke each registered device in Telegram Settings → Devices, rotate API/bot/database secrets as appropriate, provision a fresh encryption key and re-authenticate explicitly authorized accounts.

**Disable/local removal is not Telegram revocation.** Local removal deletes stored ciphertext and closes the local client. Revoke + remove calls Telegram logout for a connected session. If no connected session is available, revoke from Telegram's Devices UI or re-authenticate; local removal does not claim to invalidate it remotely.

## Queues and restrictions

Requests use only matching public targets or bot-managed private invites; arbitrary private invites are rejected because ownership cannot be checked safely before a join. Telegram approval gates are respected. Cancelling a job stops further actions; it does not undo requests or memberships already accepted by Telegram. Account owners must cancel/leave those manually when needed. Rejoin is bounded, cannot join a new call ID automatically, and stops after explicit remote self-left/kicked/group-removal signals. Ambiguous removals are treated conservatively. Before rejoining, the worker queries that same call and requires Telegram to still list the account as a participant; a missing participant is not blindly re-added.

FloodWait is persisted per account for jobs and per actor for login, and honored across restarts. There is no proxy rotation, stealth identity spoofing or flag-bypass module. Application caps do not replace Telegram's server-side limits. Call transports are interrupted by process restarts; no continuous-attendance guarantee is possible.

## Logging, notifications and retention

Application logs serialize deliberately authored context, exception **class names** and traceback filenames/line numbers, not exception messages, raw Telegram updates, request bodies, OTPs/passwords or session material. Secret configuration values are redacted. HTTP access logs and verbose third-party Telegram logging are disabled. The optional logging chat should be private; it receives operator/system event metadata, not credentials.

Mongo audit defaults to 90-day TTL. Terminal jobs expire after 30 days, successful outbox rows after 7 days and failed delivery rows after 30 days. TTL cleanup is periodic, not instantaneous. Users/plans/accounts/targets remain until administratively removed. Those personal IDs/metadata and private managed links are also sensitive; secure the database/backups.

Durable notices have idempotency keys, retries and blocked-user failures. A server crash between external Telegram delivery and Mongo acknowledgement can duplicate a notice. Notifications are best-effort external delivery, not a guarantee; grant/expiry events remain durable for retry.

## Deployment boundaries

One process/replica, private Mongo network, application-scoped Mongo user, non-root read-only app container, bounded temporary filesystem, no capabilities/new privileges, private `.env`, trusted TLS reverse proxy, no publicly published backend/database ports. Do not expose HTTP sign-in or trust arbitrary direct forwarded headers. Protect Docker/socket access, which is effectively host-admin access.

Maintain dependencies through review/test/rebuild. Compatibility alerts do not confer a guarantee of Telegram protocol compatibility. Verify your own deployment before accepting payments and maintain an incident/revocation plan.


## Cloud startup boundary (1.0.1)

The container ships public defaults, not private config or credentials. Environment-only startup still requires real credentials and positive owner IDs. A configured missing external path remains an authored startup error. HTTP liveness may be available during DB initialization/lease handover, but all login API requests return 503 until operational readiness. No Telegram account clients/polling begin before singleton leadership. Optional filesystem log failures fall back to sanitized console output instead of causing a startup crash.

A screenshot of secrets should be treated as an exposure risk. Rotate bot/database credentials as appropriate; encrypted-session keys require restoration, deliberate migration or account re-authentication. Rotating an encryption key alone does not revoke a Telegram session already copied by an attacker. No exposed screenshot value was embedded in this update.

## 1.1.0 panel metadata and display safety

UI persistence contains only message IDs, banner identity, render hash and timestamps, with 90-day expiry. It is not a role/plan cache and never stores OTP/password/QR tokens or panel bodies. The QR transient photo is excluded from durable banner handling. Decorative smallcaps preserves HTML attributes, commands/links/code and button payloads; input examples remain copyable. No historical chat-message purge or Telegram retention-erasure guarantee is made. See AUDIT.md for hardening findings and residual risks.

## 1.2.0 paid feature/quota controls

Hiding buttons is not authorization: feature checks run at create/confirm/execute/pacing/rejoin points using fresh Mongo plans. Permanent target locks are enforced in the service layer for every regular user, regardless of an old UI or locked marker. Only owner/admin corrections free slots, with role/nonce/expiry/reason/active-task safeguards and an acknowledged audit authorization. Trusted staff can intentionally override their customers' channel choices; this is the chosen policy, not a customer privilege.

Legacy missing fields preserve prior both/10-slot access (or a greater existing count). Invalid explicit feature metadata fails closed; staff can explicitly repair it. Keep the original key/database and avoid old-version rollback that drops enforcement. Staff correction reasons are user-entered audit text: never enter secrets there. The contact username is only a link, not a role grant. Health reports contain IDs/status/error types, not error messages or credentials, and skipped probes are not claimed verified. UI metadata also includes a non-secret view tag for stale-result protection.

## 1.3.0 membership/automatic call boundaries

Owner/admin are exempt from required membership so requirements can be repaired; admins cannot add/remove requirements. Membership unknown/pending/left/kicked states fail closed; short positive-cache reuse is documented. New automation checks use Access in addition to the UI guard. Stop/cancel/help/contact remain reachable.

Automatic mode is opt-in for explicitly authorized registered channels and owned pool sessions. It may establish prerequisite group membership, but never arbitrary private-invite access, a new call, microphone/camera/media output or E2E conferences. Per-channel account caps and permanent slots still apply. Manual jobs have priority; one physical chat cannot get duplicate auto shares. Original safety deadlines and blocked identities survive restart; unsafe/cancelled native transports are not reused while uncertain. Expected external Telegram/Mongo acknowledgement and distributed timing limitations still apply.

/start command cleanup waits for a response; credentials keep immediate best-effort cleanup. A sanitized raw error fallback is independent of DB/outbox/edit failures. No new module writes OTPs/passwords/session plaintext to FSM, UI metadata, logs or ZIP. Required join URLs are intentionally visible links, not session credentials; do not expose private invites unnecessarily. Existing encryption keys/DB must not be replaced on upgrade.

## 1.3.1 boundaries retained

Public does not mean authorized: direct joins still require the user's saved target, active feature, target admin control, bot invite rights, numeric entity-ID match and pacing/cooldown/caps. Public approval-required targets remain pending; no join restriction is bypassed. Private request invitations are not replaced by direct private admission.

Only owners change/preview start-photo choices. Visibility preference does not erase the saved selection or disable login QR. Known media RetryAfter stops early sends; unknown network/acknowledgement outcomes are not immediately retried. New task/audit diagnostics contain IDs/status/type/author-written hints, not raw RPC messages. The supplied real IDs were not added to tests, configuration or archives. Revocation requires the owner of the account to authenticate again.

## Capacity/lifecycle boundaries (1.3.2)

The new 100 cap is bounded and validated, not unlimited. Env override changes a non-secret deployment setting; original private config/key/database and all existing stored sessions remain. Staff read-only capacity view does not authorize ordinary users to sign in or alter plans. Concurrent completion checks are serialized; loser authorization is disposed before persistence, not taken from another saved identity. Reauth remains owned/busy-gated and consented.

Post-commit health is managed background work; a failed health load must not log out a committed session. Shutdown cancels/gathers pending tasks. Periodic health skips busy/cooldown sessions. Callback ACK/FSM/network failures do not serialize credentials into recovery responses; exact 2FA and QR cleanup remain covered.


## Unlimited and transport ownership (1.4.0)

Unlimited is an explicit commercial mode, not a safety/authorization bypass. Server resolution still bounds resources and checks role/expiry/features/target control, permanent slots, moderation, FloodWait, manual priority and durable deadlines. No automatic access is given to unrelated chats. New schema nullable values are rejected if flags are inconsistent; do not downgrade to old integer-only code without a reviewed conversion/backup plan.

Per-account native tasks/futures and shielded disconnect cleanup are owned and drained. Uncertain transports are quarantined, not reused; network cleanup never erases encrypted sessions. Native adapter internals are pinned/shape-checked and must not be blindly upgraded. Logs exclude raw asyncio task/future reprs and Telegram response text; notification diagnostics use closed categories. No global exception-handler suppression or Telegram protection bypass is used. Read [RUNTIME_LOG_AUDIT.md](RUNTIME_LOG_AUDIT.md). This is not an independent penetration/security certification.


## Saved-session recovery security boundary (1.4.1)

Automatic network/native/storage/auth failures do not delete ciphertext or call Telegram logout on saved sessions. Confirmed bans disable automation, while revoked/expired/duplicated/deactivated or mismatched authorizations stop automatic use. Preserving encrypted data is not a ban/revocation bypass. Only identity-validated session checkpoints or an explicitly authorized successful replacement update saved session material; explicit removal deletes its record. The original encryption key/database/volumes remain necessary.

Validated DC/key checkpoints and generation/connection CAS fences prevent stale tasks from overwriting or marking a replacement. Global-paced RPCs recheck live ownership/authority/waits. Temporary login clients have separate fresh authorizations; unsaved rejection cleanup cannot be applied to an acknowledged or ambiguously committed saved key. An uncertain write can leave an unused Telegram device authorization for deliberate review; no zero-orphan/zero-downtime claim is made.

Recovery cannot override staff disables/removals, customer locks, moderation blocks, FloodWait or host ceilings. Wrong-key storage failures retry local validation without issuing OTP and can recover after restoring the original key; missing legacy ciphertext cannot be recreated. Sessions/checkpoints are encrypted in Mongo, with no plaintext fallback journal. Protect backups and the separate original key. Nested bytecode, local session files and private config are recursively excluded from the Docker build context. See [SESSION_RECOVERY.md](SESSION_RECOVERY.md).


## Operator-selected host verification (1.4.2)

Run the reader inside the existing app environment; do not create a second Telegram user-session runtime. The reader uses no StringSession/TelegramClient, does not decrypt session ciphertext, creates no indexes, takes no lease and writes no account/settings records. It calls getMe once and reads only loopback HTTP plus aggregate/count metadata. Reports exclude identifiers, request details, private URIs/tokens/keys and internal references. Argument/config/network failures do not echo supplied secret values.

The staff health observer uses existing authorized pool clients for one bounded read-only existing-call sample; it never joins/creates a call, publishes/records or bypasses deadline/moderation/cooldown. Local normal pool pacing/FloodWait enforcement still applies. One bounded settings export uses runtime/bot/version and a private per-runtime keyed config attestation; its digest is not exported to the user report. This detects accidental changed key/config, not an independent security certification or proof against a compromised database/host.

Native call authorization is rechecked after waits/callbacks and SDK completion. This closes the queued disable/replacement/FloodWait/moderation race without changing commercial entitlements, target locks or encrypted-session preservation. See [HOST_VERIFICATION.md](HOST_VERIFICATION.md).


## Transport errors and future ownership (1.4.3)

Only the existing per-client sender is instrumented; no additional user client/session/runtime, global asyncio exception filter, global SDK method replacement or library version upgrade is introduced. Future observation retrieves exceptions but does not change what awaiters receive. SDK callback/queued work is retained and drained before pool replacement. Ordinary DC migration remains distinct from permanent pool retirement.

Transport classification uses only exception class and bounded numeric code, not packet/error text. 404/AuthKeyNotFound does not prove a ban/revocation; wire 429 has no server retry-after and therefore uses an explicit conservative local minimum. Known longer waits win. No new OTP, logout, key rotation, authorization reconstruction or bypass occurs automatically. Terminal loss closes only that adapter's callback gate; offline cleanup is local, not an invented successful Telegram leave. Original encrypted credentials, protected auth stops, staff changes and generation/epoch fencing remain intact. See [TRANSPORT_RECOVERY.md](TRANSPORT_RECOVERY.md).


## Confirmed session conflicts (1.4.4)

A confirmed AuthKeyDuplicatedError is an already-invalidated authorization, not a licence to retry/bypass Telegram's main-session restriction. The first observation gates additional managed identities and SDK reconnect/write paths. No ciphertext/key deletion, automatic OTP/logout, IP rotation or PFS/parallel-session bypass is introduced. Independent official-app authorizations are not the same as reusing a copied key.

Server-clock/majority lease ownership and conservative monotonic wire deadlines constrain cooperating runtimes sharing this database. They cannot stop an old version/other tool/database clone; operator inventory remains necessary. Admins may view safety; only owner-reviewed, nonce/expiry/incident-bound, audited confirmation can resume after owned cleanup. It does not clear account revocation/ban flags. Read-only diagnostics expose no credentials, process arguments or provider identifiers and do not pretend to verify every host. See [SESSION_SAFETY.md](SESSION_SAFETY.md).
