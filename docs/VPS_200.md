# TelePilot 1.5.0 — 200-account Docker VPS profile

Designed configuration: **one Linux x86-64 VPS, 8 vCPU, 64 GB RAM, one app worker, up to 200 saved managed accounts**. Use authorized accounts and targets only. This is not evidence of 200 simultaneous live Telegram/RTC connections, nor an uptime/no-ban/no-revocation guarantee. The supplied acceptance tests use synthetic Telegram/RTC outcomes and real disposable Mongo/HTTP.

> **Upgrading or moving an existing bot? Do not run setup, generate another encryption key, overwrite private config, change the Compose project identity, or start a second copy. Read section 3 first.** Existing invalidated Telegram keys cannot be repaired by adding RAM or restarting; follow [SESSION_SAFETY.md](SESSION_SAFETY.md).

## 1. What this release changes

- Pool enrollment and finite per-task account allowances support **1–200**, including completion races at the last slot and reauthentication at a full pool. New finite Premium defaults remain **5**, not 200. Existing finite 5/7/20/100/custom allowances remain finite and unchanged. Explicit account/channel `unlimited` remain independent and include future eligible accounts, subject to the host ceiling.
- Staff health scans review all **200**, release the lifecycle lock between accounts and during UI notifications, and re-read each account's current state. Owner/staff actions need not wait for an entire paced fleet scan. Busy calls, cooldowns, rejected authorizations and the fleet safety pause still prevent unsafe probes.
- Host verification reports up to 200 identity proofs. Target corrections cannot overlook busy automatic account 101–200. Allocation, lightweight recovery, shutdown, fair sharing and manual priority have additional 200-record/slot regressions.
- VPS profiles raise container process/file limits and give a 30-minute manual health budget. This does **not** increase Telegram pacing or native connection concurrency.
- Persistent volumes, `restart: unless-stopped`, Docker health checks, startup-at-boot instructions and an optional **host-side unhealthy watchdog** support unattended operation. A watchdog does not resume session safety or repair invalidated keys.

### Resource envelope

| Component | CPU ceiling | RAM ceiling | Other |
|---|---:|---:|---|
| app | 6 vCPU | 48 GiB | 4,096 PIDs/threads, 65,536 open files, 300s stop grace |
| bundled Mongo | 1 vCPU | 8 GiB | 6 GiB WiredTiger cache, 65,536 open files, 120s stop grace |
| host / spare capacity | remaining | remaining | OS, Docker, SSH, filesystem/cache, optional HTTPS proxy |

At 64 **GiB** total, these ceilings leave 8 GiB; a provider advertising 64 decimal **GB** leaves roughly 3.6 GiB. These are ceilings, not preallocated RAM or measured per-account requirements. Use SSD storage with backup space; monitor actual disk, threads, memory and CPU. External Mongo runs elsewhere; the external profile starts no local database. The base small-host Compose limits are not the 200-native-instance resource profile: use the files below on this VPS.

## 2. Fresh installation ONLY

Requirements: current Docker Engine + Compose v2 on a maintained Linux x86-64 distribution, Python 3 for the **host setup script only**, and enough SSD capacity. The app and dependencies run in Docker. Install Docker from its supported distribution instructions, then enable its daemon:

```sh
sudo systemctl enable --now docker
```

Extract the ZIP so the source lives at `/opt/telepilot`, then:

```sh
cd /opt/telepilot
python3 scripts/setup.py --profile vps200
```

Setup requests your own API credentials, bot token, numeric owner ID and optional external Mongo/HTTPS settings. Secret prompts are hidden. It creates a fresh encryption key **only for this new installation**, refuses to overwrite an existing `.env`, writes `.env` mode 600 and emits exactly one start command for the selected profile. Do not share that file.

Choose a stable Compose project name **on this fresh install only**, for example add `COMPOSE_PROJECT_NAME=telepilot` to the new `.env`. Keep that name for every subsequent command and upgrade. Without an explicit name, Compose derives one from the source directory; renaming that directory can select different volumes.

### A. Bundled persistent Mongo

```sh
docker compose -f compose.yaml -f compose.vps200.yaml config --quiet
docker compose -f compose.yaml -f compose.vps200.yaml up -d --build
docker compose -f compose.yaml -f compose.vps200.yaml ps
docker compose -f compose.yaml -f compose.vps200.yaml logs --tail=80 app
```

The app and Mongo retain `unless-stopped`; `mongo_data` and `app_data` are named persistent volumes. Mongo has **no published port**. The JSON config is mounted read-only, app root is read-only/non-root, capabilities are dropped and logs rotate. The bundled profile inherits a bounded 64 MiB `/tmp`; the standalone external profile uses 256 MiB.

### B. External persistent Mongo (including a move from another provider)

```sh
docker compose -f compose.vps200.external.yaml config --quiet
docker compose -f compose.vps200.external.yaml up -d --build
docker compose -f compose.vps200.external.yaml ps
```

Use this file **by itself**, not with `compose.yaml`. It requires no irrelevant local Mongo root/app passwords and starts no unused second Mongo. Set the original `MONGO_URI` and original `MONGO_DATABASE`; URI authentication database and application database are not always the same. Restrict database access to the VPS, require appropriate authentication/TLS and keep backups off-host.

Default login is **private-chat phone → OTP → exact optional 2FA**, with QR alternative. No public login website is required. HTTP binds to container 0.0.0.0 but is published on **host loopback 127.0.0.1:8080 only**. To use the optional domain/proxy, append `-f compose.https.yaml` to the selected Compose command and keep valid `PUBLIC_DOMAIN`/`TLS_EMAIL`; expose 80/443 for Caddy, not Mongo. Browser login remains an explicit opt-in.

## 3. Upgrade / migration without losing saved data

1. **Identify the running deployment first.** List projects with `docker compose ls`; inspect the existing app's Compose project label privately if needed. Do not invent a new project name. Find the original private `.env`, `config.json`, encryption key, database name/URI and volumes.
2. Take a verified, access-controlled database backup and save the original private configuration/key securely. Back up volume data with a database-consistent method. Do not restore a backup into a simultaneously running second worker.
3. Stop all other deployments, old provider workers, cloned databases used by another bot, local tools and other processes using these **same managed Telegram keys**. Do not run a new bot alongside the old one, even on the same IP. If the topology is uncertain, keep session safety paused until reviewed.
4. **Extract the new ZIP into a separate staging directory.** The archive's `config.json` is a public template, not your private file. Never unzip it over a live private config. Copy/update source into the original project directory while excluding `.env`, private `config.json`, `data/` and existing volumes; alternatively copy both original private files into the staged source and explicitly retain the old Compose project name/volumes. Do not copy runtime/session files to another active bot.
5. Keep **exactly the original** `SESSION_ENCRYPTION_KEY`, API credentials, `MONGO_URI`, `MONGO_DATABASE`, owner configuration and persistent volumes. Do not run `scripts/setup.py` or `scripts/generate_key.py` for this migration. Blank optional VPS `OWNER_IDS`, `MONGO_DATABASE` and `PUBLIC_BASE_URL` passthrough no longer erases nonblank private JSON values; set actual values explicitly if moving from environment-only hosting. Only variables explicitly listed in the chosen Compose file are forwarded: copy any other environment-only setting (for example a disabled `calls_enabled`, custom UI/timezone or logging setting) into private `config.json` before moving. Merely putting an unlisted variable in `.env` does not inject it into a Compose container.
6. For bundled Mongo, use `-f compose.yaml -f compose.vps200.yaml` under the **original project identity**. For existing external Mongo, use only `-f compose.vps200.external.yaml`, also under that same identity if retaining Docker volumes. If moving providers, shut down the old bot before starting Docker with the original external DB/key. The distributed Mongo lease/wire fence is additional protection, not proof that unrelated copies are absent.
7. Validate with `config --quiet` and rebuild/start using the matching section-2 command. Check readiness, `/start`, **manage bot → pool capacity**, `/accounts` and `/sessionguard`. The pool should show an effective capacity of **200**. The profile intentionally overrides a stale old `MAX_POOL_ACCOUNTS=100` or JSON cap of 20. A deliberate lower host cap can be set with `VPS_MAX_POOL_ACCOUNTS=100` (or another 1–200 value).
8. Existing finite subscriber quotas do not expand. Staff can deliberately grant a finite 200-account allowance, or use independent `unlimited`, through the existing Premium flow. Target slots remain locked; roles, feature tiers, moderation, manual priority and all existing safety controls remain enforced.

Do **not** use `docker compose down -v`, delete Mongo volumes, reset the database, replace the key, or reset rejected account flags to make a panel look healthy. After a confirmed duplicate-key incident, stop conflicting copies, complete owner review, then freshly authenticate the authorizations Telegram actually invalidated. Repeated OTP/login/restart loops are not recovery.

## 4. Boot, health and unattended operation

`unless-stopped` restarts an exited/crashed container and starts eligible existing containers when Docker starts after a host reboot. It intentionally respects a deliberate stop. Enabling `docker.service` is required. It does not recreate a deleted container and **does not, by itself, restart a merely unhealthy but still-running container**.

The application has wakeable temporary-failure recovery, bounded retries/backoff, persisted Telegram waits, singleton ownership, native cleanup and nonblocking roster loading. A newly booted 200-account pool takes time to reattach safely. The global 2-second MTProto pacing, 3 automatic connection setups, per-account join limits, call deadlines and 360-minute default call cap remain unchanged. Even 200 successful paced identity RPCs alone take roughly 400 seconds; cold attach/migration/waits can take longer.

`MANUAL_HEALTH_TIMEOUT_SECONDS=1800` is the VPS default (validated range 15–1800; ordinary config default 600). A timed-out/partial scan is **not** a successful 200-account health proof. Busy accounts stay skipped rather than being disconnected for a test. `/start` and staff navigation remain available while the pool loads and scans run.

### Optional unhealthy watchdog (systemd HOST only)

Install this only if you want automatic handling of a genuinely unhealthy/hung container beyond Docker's exit restart policy. The script uses only Python's standard library and Docker metadata; it reads no Telegram session/key/database and never creates/scales containers or clears the safety pause. Docker-socket access is host-admin authority; install only source you trust.

First set the **actual existing Compose project name**, not a new name:

```sh
sudo install -m 600 /dev/null /etc/telepilot-watchdog.conf
sudoedit /etc/telepilot-watchdog.conf
# File content: TELEPILOT_COMPOSE_PROJECT=your_actual_existing_project
```

Test with the same explicit name (replace the example with the real one):

```sh
sudo python3 /opt/telepilot/scripts/health_watchdog.py --project your_actual_existing_project --dry-run
```

Then install the opt-in timer. Adjust `ExecStart` in the service **first** if your source path is not `/opt/telepilot`; `ProtectHome=true` means the executable must not live under a protected home directory.

```sh
sudo install -m 644 deploy/systemd/telepilot-watchdog.service /etc/systemd/system/
sudo install -m 644 deploy/systemd/telepilot-watchdog.timer /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now telepilot-watchdog.timer
sudo systemctl list-timers telepilot-watchdog.timer
```

Behavior:

- Waits 10 minutes after boot, checks about every 2 minutes, and serializes runs with a per-project lock.
- Refuses zero/multiple matching app containers, invalid/unknown health metadata, unsafe/corrupt state or unavailable Docker. Does not start an app already observed stopped/restarting.
- Only an existing **running + unhealthy** app is eligible. Re-checks state immediately before requesting a restart of the **same container**, with 300s stop grace; the old process stops before the replacement starts.
- Throttles to at most one requested restart per 15 minutes, persisting the throttle before Docker is called, including a CLI timeout. No `docker run`, replicas, automatic reauth or volume deletion.
- Healthy or starting apps are left alone. A healthy API with **session safety paused** stays paused; restarting is not owner approval.

**For deliberate maintenance stop the timer first**, then stop the app with the matching Compose files. This avoids a race between an independent manual stop and the watchdog's final inspect/restart. Leave the timer off while investigating session conflicts or performing backups/upgrades.

```sh
sudo systemctl stop telepilot-watchdog.timer
# Now use your matching Compose command: ... stop app
# After investigation/maintenance and one-worker checks:
sudo systemctl start telepilot-watchdog.timer
```

Inspect watchdog outcomes with `journalctl -u telepilot-watchdog.service`; output is a small sanitized status/reason, not raw `docker inspect` or secrets. Stop the timer and investigate repeated failures instead of accelerating restarts.

## 5. Acceptance and ongoing checks

1. Start with a few authorized accounts, confirm saved-session recovery and an owned test call, then add accounts gradually. Do not mass reauthenticate invalidated keys before the conflicting deployment has stopped.
2. Monitor `docker stats`, disk use, PID/thread counts, host logs and rotated app logs while ramping up. Resource limits are safeguards, not a 200-RTC performance certificate. If actual usage approaches the limits, reduce workload and investigate; do not lower pacing or disable session ownership.
3. Run `/health` in the **existing bot**, preferably during one already-owned managed call; wait for the result. Then run the read-only reader **inside that same app container** with your selected Compose files:

```sh
# Bundled Mongo example; use the external file alone for that deployment.
docker compose -f compose.yaml -f compose.vps200.yaml exec -T app python scripts/live_check.py
# Safety-only diagnosis, without account/call joins or new clients:
docker compose -f compose.yaml -f compose.vps200.yaml exec -T app python scripts/live_check.py --scope safety
```

A reader result of incomplete (exit 2) without a current identity/call proof is honest, not a reason to request new OTPs. [HOST_VERIFICATION.md](HOST_VERIFICATION.md) and [LIVE_ACCEPTANCE.md](LIVE_ACCEPTANCE.md) specify the manual checks. A call sample verifies one native/server participant, not all 200, media quality or permanent attendance.

Keep encrypted off-host backups of the original key plus database, check restore procedures without running duplicate managed sessions, retain SSH access and monitor provider/network outages. Software can recover many temporary failures, but it cannot promise permanent operation, prevent Telegram from revoking/banning accounts, restore a server-invalidated authorization, or remove the need for incident review.
